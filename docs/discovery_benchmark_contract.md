# The discovery benchmark contract

This document defines the learning problem this benchmark exists to
measure:

> **How can an RL agent efficiently adapt when failures reveal
> previously hidden information about the environment?**

It formalizes the unit of evaluation, the suites, the metrics, the
anti-leakage rules, and the train/validation/test protocol. It is a
design contract: nothing here implements a new algorithm or imports a
new game. Task inventory and per-task decisions live in
`manifests/discovery_task_candidates.toml`; the audit evidence behind
them is regenerated by `python scripts/audit_discovery_candidates.py`.

Throughout: **IWBTGR means *I Wanna Be The Guy: Remastered* 1.5.3
(`iwbtgr_1_5_3`, GameMaker 8.2 / Yuuutu engine) — it is NOT the
original 2007 MMF2 *I Wanna Be The Guy*** (`iwbtg_original_2007`,
whose import is a separate, currently-gated track:
`docs/iwbtg_mfa_feasibility.md`). The two are never conflated, per
`docs/fidelity_contract.md`.

---

## 1. Unit of evaluation: a task containing multiple attempts

The benchmark's unit is a **task**, not an episode. A task is the
experience of standing at one fangame checkpoint in front of one
trapped screen: the trap does not change between deaths, and dying is
how you find out what the trap is.

A task τ is the tuple

```
τ = (game_id, room_id, checkpoint, goal, θ, K, H)
```

- **game_id / room_id / checkpoint** — a fixed screen or segment of a
  fixed game version, and a fixed start state: the checkpoint's stored
  player position, facing, `vspeed=hspeed=0`, `djump=1`, plus the
  room-entry state the source game restores there (difficulty, cart
  state, room-entry flags). This is exactly the source-faithful
  respawn state already specified in
  `docs/action_and_reset_semantics.md`.
- **goal** — a completion predicate on the environment state (reach a
  target region / activate a target save / complete a warp), fixed per
  task and declared in the manifest.
- **θ** — the task's **hidden configuration**: the authored latent
  hazard/event behavior of the segment (which blocks are fake, which
  fruits are wired to which invisible trigger rectangles, which
  platforms collapse, the laser schedule's frame table, …). θ is part
  of the task definition and **remains fixed across all attempts** of
  the task. Any environment stochasticity (the enumerated RNG call
  sites in `docs/iwbtgr_nonboss_mechanics.md` §RNG) is drawn from a
  seed that is part of τ and is restored on every attempt reset, so
  within a task the world is exactly repeatable and hidden information
  is learnable rather than a moving target.
- **K** — the attempt budget; **H** — the per-attempt frame budget.

**Attempt.** An attempt is a rollout from the checkpoint state until
death, goal, or H frames. Death ends the attempt and triggers an
**attempt reset**: the source-faithful checkpoint restore (full room
reset — objects, gates, bullets recreated; player recreated at the
stored position; progression state persists), i.e. `attempt_reset()` /
`checkpoint_respawn=True` semantics, unchanged.

**Task lifecycle.** The task runs for up to K attempts or until the
first success, whichever comes first. Timeout of an attempt (H frames
without death or goal) consumes the attempt.

**Memory rules.**

- Agent-side recurrent/episodic memory **may persist across attempt
  resets** within a task. This is the point of the benchmark: the only
  bridge between a death and the next attempt is whatever the agent
  carries over.
- **All agent memory must be cleared on task reset** (`env.reset()`),
  including recurrent state, episodic buffers, per-task adaptation
  parameters, and any test-time-learned weights. Evaluation harnesses
  must enforce this; a result that lets state leak across tasks is
  invalid.
- The environment carries nothing across attempts on the agent's
  behalf beyond what the source game itself persists (activated saves,
  progression flags, death counter) — all of it world state, none of
  it hazard information.

## 2. Formalization: partially observable multi-attempt RL

Fix a task distribution 𝒯. Each τ ∈ 𝒯 induces a POMDP with structured
resets:

- **Environment state** s_t = (w_t, θ): the full simulator state w_t
  (player kinematics, every entity's position/phase/armed state,
  timers, flags) plus the static hidden configuration θ.
- **Observable state** o_t = ω(w_t): the rendered scene and
  proprioception under the discovery observation profile (§7). ω is
  *manifestation-limited*: θ is never observed directly, and hidden
  hazards enter o_t only once they manifest in w_t (a launched fruit
  is visible while flying; an unarmed fire, a fake block, an invisible
  trigger rectangle, and a future schedule are not).
- **Latent hazard information** θ: everything about lethality that ω
  withholds until manifestation. θ is fixed within a task (§1) and
  varies across tasks.
- **Attempt reset** ρ_a: w ← w₀(τ) — the checkpoint restore. It
  resets the world, not the agent: the agent's internal state h is
  untouched.
- **Task reset** ρ_τ: draw a new τ; h ← ∅.
- **The information in a death trajectory.** A failed attempt i
  contributes its full observed trajectory
  ξᵢ = (o₁,a₁,…,o_{tᵢ}, death event) to the agent's history. The death
  event itself carries only what the game shows: the terminal
  observation and where/when the attempt ended. Conditioned on the
  attempt-reset structure (same w₀, same θ), ξᵢ is evidence about θ:
  e.g. a death at position p to a hazard that was not visible at p one
  frame earlier localizes a hidden killer near p; surviving past a
  suspected trap is evidence of its absence. Formally the agent
  maintains a policy π(a_t | o_{1:t}, ξ_{1:i−1}) and the benchmark
  measures how efficiently the posterior over θ implied by past
  failures is converted into success.

The objective on a task is success within the budget:
J(π, τ) = P[∃ attempt i ≤ K that reaches the goal]. The benchmark
reports J and the attempt-indexed curve (§6) over held-out tasks.

**What distinguishes this from ordinary episodic RL:** in the standard
protocol every episode i.i.d.-resamples the world, so dying teaches a
*policy gradient*, not a *fact*. Here death i and attempt i+1 share θ
by construction, so a single failure has identifiable, reusable
content, and the measurable question is whether one exposure suffices
(§6, repeated-death rate) — a per-task, within-lifetime quantity that
episodic return curves do not expose.

**Discovery task criterion.** A task belongs to the discovery suites
only if both hold:

- (i) **initial ambiguity**: given o₁ (and any amount of pre-task
  knowledge that excludes this screen — see splits, §8), at least two
  materially different hazard configurations are consistent with the
  first observation, and plausible first-attempt behaviors differ in
  outcome across them (a fake block vs a real one; a fruit that is
  wired vs unwired; a floor that holds vs collapses);
- (ii) **informative failure**: the failure trajectory separates those
  configurations — after the death, an attentive agent can act
  differently *for a reason contained in ξ*.

Tasks failing (i) are precision/timing content (visible spikes, visible
patrolling enemies, observable schedules): they belong to the existing
skill benchmark, not the discovery suites, and are recorded as
excluded in the manifest with evidence.

## 3. Suites (separately reported, never pooled)

**S1 — IWBTG-native (headline).** Source-native screens/segments of
IWBTGR 1.5.3 (`iwbtgr_1_5_3_v1` frozen pack), selected by the audit in
§4 and enumerated in the manifest. Every task's content is
content-exact under the frozen pack's deviation ledger
(`docs/iwbtgr_known_deviations.md`); labels are per-task in the
manifest. **When — and only when — the original-2007 import is
genuinely available** (the `mfa2pack` track clears its blockers and
produces a validated pack; no fabricated content, no placeholder
screens), original-2007 screens join S1 as their own subset
(`iwbtg_original_2007.*` ids), reported both separately and combined.
Until then the headline is explicitly "IWBTGR (Remastered)".

**S2 — controlled discovery.** Explicitly labeled research rooms
(`iwannagym_research_v1`): the audited subset of the 20 trap rooms plus
future **counterfactual variants** for causal ablations — the same
layout with the hazard disarmed / relocated / retimed / replaced by its
decoy twin, generated from the same room source with a declared edit.
These rooms are original content in fangame style, never presented as
any shipped game. S2 exists because native content is finite and fixed:
causal claims ("the agent used the death, not a layout prior") need
counterfactuals no shipped game can provide.

**S3 — OOD transfer.** Tasks from other imported classic games —
first `k2warped_gms14`, later imports as they land — evaluated
zero-shot and few-attempt after training on S1/S2 only. **S3 is never
pooled into the headline IWBTG number.** Status note: the K2W import
is static-world today; its trap objects (1,111 `objBlockFake`, 559
`objBlockInvis`, moving spikes, triggers) are inventoried but not yet
dynamic, so S3 has candidate rooms and zero accepted tasks until the
K2W dynamics milestone (recorded in the manifest as `pending`).

## 4. Audit: native screens and existing trap rooms

`scripts/audit_discovery_candidates.py` classifies every placed
instance in every IWBTGR gameplay room by *how its lethality becomes
observable* (intrinsically hidden/deceptive vs trigger-dependent vs
visible), buckets them per 800×608 screen, and attaches the nearest
checkpoint anchor. Findings (full JSON:
`build/source_reports/discovery_screen_audit.json`):

- Hidden-hazard content is heavily clustered: rGuy1 (47 intrinsic + 46
  invisible trigger rectangles wiring 182 fruit), rFactoryOutskirts
  (140, dominated by the 121-block appearing-Yoku chains),
  rMetroid (83, sinking platforms + metroid traps), rGuyRoad (72, cart
  segment), rGuyFortress2 (51), rGraveyard (38 + 27 triggers),
  rGuyFortress1 (29, unarmed-fire cascade + collapsing floors).
- Rooms that are **precision-only** at screen granularity: rGuyTower
  (one trigger in 368 instances), rGuyLabyrinth (six thinly spread
  fake blocks in a visible-spike maze), rZelda, rGuyEntrance (single
  orb-gated kill tied to global progression). These are excluded from
  S1 with the evidence recorded per row in the manifest.
- **Mass static-fruit screens are not discovery content**: rGuy1
  screen (1,0) holds 160 cherries and zero triggers — a needle wall,
  fully visible. The audit counts trigger-dependent statics as hidden
  only where trigger rectangles coexist.
- Boss rooms are excluded from the discovery suites v1: fights
  conflate hazard discovery with long-horizon dexterity and phase HP
  state; they remain the existing boss benchmark. Recorded per row.

The 20 research trap rooms were audited against criterion §2
(initially-ambiguous hazard + informative failure): 16 qualify as
controlled discovery tasks; `t07_bullets`, `t15_rain`, `t16_bridge`,
`t19_speedgate` are timing/observation rooms (their schedules manifest
without a failure) and stay in the skill set — each decision with its
reason is a manifest row.

## 5. Task anatomy (what the manifest records)

Every candidate row in `manifests/discovery_task_candidates.toml`
records: stable task id (`disc.<game>.<room>.<slug>`), game/version,
room + start checkpoint (source coordinates), goal predicate, attempt
budget K and per-attempt frame budget H, hazard family/families, what
information is initially unavailable, what a failure (or in-attempt
observation) reveals, source-native vs controlled status, fidelity
label with provenance, proposed split, and the inclusion/exclusion
decision with evidence. Defaults: K = 25, H = 2,000 frames (40 s at
50 Hz; cart and multi-screen segments override upward). Room speed is
part of the task (rGuyRoad/rMetroid/rGuyFortress1/2 run 30 Hz logic in
the source — recorded per task).

## 6. Primary metrics

All metrics are computed by the **evaluator** from recorded
trajectories plus the task manifest — never from privileged policy
inputs (§7). For a task set T, with per-task attempt outcomes:

1. **Success@K** — fraction of tasks solved within K attempts.
2. **Success-versus-attempt curve** S(k) = fraction of tasks solved
   within the first k attempts, k = 1..K, and its normalized AUC,
   `AUC = (1/K) Σ_k S(k)` ∈ [0,1] (1.0 = everything solved on attempt
   1; S(1) is the zero-knowledge/zero-shot point of the curve).
3. **Attempts (=deaths+timeouts) to first success** — median and IQR,
   censored at K (report censoring rate).
4. **Frames to first success** — total environment frames across
   attempts until the first successful attempt completes, censored at
   K·H.
5. **Repeated-death rate (RDR)** — among deaths after the first, the
   fraction attributable to a hazard **already observed** in the same
   task: the evaluator attributes each death to a hazard instance
   (post-hoc, from simulator state), and a hazard counts as observed
   if it previously killed the agent in this task or previously
   manifested inside the agent's rendered view during this task. Low
   RDR = the agent converts exposures into avoidance; RDR near the
   memoryless baseline falsifies adaptation claims.
6. **Post-discovery improvement / regret** — improvement:
   ΔP = P(pass hazard | ≥1 prior in-task exposure) − P(pass hazard |
   first exposure), pooled over hazard passages; regret: extra
   attempts spent beyond an informed scripted reference policy for the
   task (the probe-policy attempt count from the manifest evidence,
   where available).
7. **Transfer** — on held-out tasks (§8): zero-shot S(1), and
   within-task adaptation gain `AUC − S(1)`. The pair separates "knew
   it already" from "learned it during the task"; S3 reports the same
   pair across games.

Sample- and wall-clock efficiency reporting for training runs is
required by §10; the metrics above are all evaluation-time.

## 7. Anti-leakage contract

The **standard policy interface** receives, per step: the discovery
observation profile (below), the running attempt index within the
current task, and its own reward signal. Nothing else. Specifically,
the policy must NOT receive:

- trigger rectangles, trigger wiring, or any invisible region geometry;
- dormant/armed flags, or any entity attribute distinguishing a decoy
  from a live hazard before it manifests (a fake block must be
  indistinguishable from a real one; a `FakeFallingSpike` from a
  `FallingSpike`);
- future event schedules (laser frame tables, Yoku chain order, the
  tetris timeline);
- hidden-killer labels or any "deadly" bit for entities whose
  deadliness is not readable from the rendered scene;
- exact hazard class identifiers beyond what rendering distinguishes;
- task IDs, room IDs, or any code that identifies a memorized layout
  (the `info` dict fields `game_id/room_id/checkpoint_id/…` are
  **evaluator-facing**; harnesses must not feed them to the policy);
- evaluation-only diagnostics (death attribution, RDR bookkeeping,
  per-hazard exposure state).

**Audit findings against the current runtime (must be fixed before S1
results are reported; recorded here so they cannot be papered over):**

- **L1 — structured obs leaks unmanifested entities.** The 6-nearest-
  entity channels (`c_src/iwanna.h`, obs builder) exclude triggers and
  markers but include active, invisible exact-layer entities: an
  unarmed `Fire` (maskless in source), a `BoltTrap`/`Grabby` before
  activation, and fake blocks appear as typed entities with a signed
  "deadly" feature. A discovery observation profile must filter the
  entity channels by **source visibility/manifestation** (would the
  source draw it with a live mask this frame?).
- **L2 — the renderer color-codes dormancy.** `iwanna_gym/render.py`
  draws classic dormant traps in a distinct `TRAP_DORMANT` color. In
  fangames the whole trick is that a trap spike looks exactly like a
  static spike. The discovery render profile must draw unmanifested
  hazards as their decoy appearance (or not at all, matching source
  visibility).

Defining `obs_profile="discovery"` (structured + pixel) with these two
fixes is the first implementation step after this design milestone; S1
acceptance is conditional on it.

## 8. Train/validation/test separation

Splits are by **screen and hazard family**, never merely by seed:

- **Screen-level rule**: a test task's screen/segment never appears in
  training under any observation profile, reward, or auxiliary task —
  including as part of a longer segment. Rooms may straddle splits
  only at screen granularity with non-overlapping camera regions.
- **Hazard-family rule**: at least one hazard family per test task is
  *family-held-out* — no instance of that family (or its controlled
  analog) appears in any training task. The proposed split holds out,
  e.g., `couchTrap`, `Higger`, `FactoryYoku`, and `metroidTrap`
  entirely (see manifest `split` fields).

Why this prevents trap memorization: with fixed content, a policy
trained on the same screens can compile θ into its weights and score
perfectly with zero within-task adaptation — the benchmark would then
measure memorization. Screen-level exclusion removes layout lookup;
family-level exclusion additionally removes "I know what couches do in
this benchmark" priors, so first-attempt behavior on a test task is
genuinely under ambiguity (§2 criterion (i)) and any AUC−S(1) gain must
come from within-task discovery. Native content is finite (S1 test is
small); the identical protocol on S2's generated variants provides the
larger-N statistical companion, reported separately.

Seeds: evaluation seeds are disjoint from training seeds *in addition
to*, never instead of, the rules above.

## 9. Paper-facing problem statement and falsifiable claims

**Problem statement.** Hard precision platformers institutionalize a
learning pattern humans execute in seconds: commit to a plan, die to a
hidden trap, and immediately re-plan around the single bit the death
revealed. The I-Wanna genre is this pattern distilled — thousands of
screens whose difficulty is *epistemic* (what is hidden) rather than
purely motoric (how precisely to move) — and it comes with an exact,
deterministic, checkpointed simulator at millions of steps/s. We
formalize each trapped screen as a multi-attempt task with fixed latent
hazard state, where death is both the failure signal and the
information channel, and ask: how efficiently can an agent convert
failures into later-attempt success, without leaking the hidden state
through the observation and without letting cross-task memorization
impersonate within-task discovery?

**Benchmark claims (each falsifiable by the stated measurement; none
presumes memory helps):**

- **B1 (discovery ≠ precision).** On accepted discovery tasks, a
  strong memoryless policy evaluated under the anti-leakage contract
  shows a materially flat success-versus-attempt curve
  (AUC − S(1) ≈ 0), while on the excluded precision-only control tasks
  its S(1) can be driven high by training. Falsified if memoryless
  policies show large within-task gains on the discovery set (the
  hidden state was observable after all — a §7 leak or a §4
  misclassification).
- **B2 (failures carry sufficient information).** For every accepted
  task, a scripted reference policy conditioned on the previous
  attempts' death evidence solves the task in strictly fewer median
  attempts than the same scripted policy without it. This is testable
  before any learning; a task violating it gets re-audited or dropped.
- **B3 (splits defeat memorization).** A policy trained to high
  Success@K on the training split without cross-attempt memory drops
  to near-baseline S(1) on family-held-out test tasks. Falsified if
  test S(1) stays high — the split leaks (shared layouts/decoys) and
  must be repaired before any adaptation result is claimed.
- **B4 (repeated deaths are measurable waste).** RDR separates agent
  classes: agents with cross-attempt state can achieve materially
  lower RDR than memoryless agents at matched S(1). Falsified if RDR
  is indistinguishable across classes — then either the tasks don't
  reward remembering (audit failure) or RDR's attribution is too noisy
  to report (metric failure); either way the benchmark, not the
  algorithm, is corrected.
- **B5 (deception breaks shaping).** On deception-family tasks (fake
  blocks, decoy spikes, fake exits), dense distance-to-goal shaping
  produces *worse* AUC than sparse reward under identical budgets,
  extending the repo's dotkid/endless observation to hidden-information
  content. Falsified if shaping is neutral or helpful there.

Whether any *particular* memory architecture (RNN, episodic, in-context
adaptation) exploits the structure is an experimental question the
benchmark is built to answer — not a claim it makes.

## 10. Cross-cutting systems contract

- **One task interface.** Every accepted task in every suite is
  loadable through the single native path used by the PufferLib
  binding: task id → (pack, room, checkpoint, goal, budgets) resolved
  from the manifest, `c_reset`/`c_step` semantics unchanged, attempt
  resets handled inside the core exactly as today
  (`checkpoint_respawn=1`), vectorized without Python in the loop.
  A Python-side `IWannaEnv(task="disc….")` constructor and a task-table
  loader for `binding.c` are the implementation deliverables; no task
  may require bespoke env code.
- **Dual efficiency reporting.** Every future result reports both
  sample efficiency (metric vs environment frames, at declared
  frame budgets) and wall-clock efficiency (steps/s achieved, total
  train wall-clock, hardware) — the engine's ~5M steps/s tiles-only /
  ~10⁵ steps/s entity-heavy range makes wall-clock a first-class axis,
  and `iw_bench_n` returns seconds (divide; see the performance
  report).
- **Rollout artifacts without hot-path rendering.** Training and
  evaluation run headless. Because replay is deterministic (seed +
  action sequence ⇒ bit-identical trajectory, asserted in the test
  suite), the evaluator records per-attempt `(task_id, seed, actions,
  outcome)` and renders offline: required outputs are (a) per-task
  success/failure GIFs via the existing `scripts/record_gif.py` /
  `record_room_gif.py` path, and (b) a metric dashboard generated from
  evaluator JSONL (`one line per task: id, suite, split, outcomes per
  attempt, S(k) inputs, RDR ledger`) into a static report. Rendering
  never runs inside the training loop.

## 11. Acceptance status of this milestone

Headline suite: IWBTG-native (IWBTGR now; original-2007 gated on its
import). Supporting suites: controlled discovery (research rooms,
labeled), OOD transfer (K2W, pending dynamics). Learning-across-deaths
is measurable via §6 on the §1 task unit; every metric is computable
evaluator-side without privileged policy inputs; the two runtime leaks
found by the audit are recorded in §7 and gate S1 result reporting. No
original-2007 content exists in any suite today, and nothing above
claims otherwise.
